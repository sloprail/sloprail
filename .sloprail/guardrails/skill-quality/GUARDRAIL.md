# The skills must themselves be high-signal

A skill is loaded into a context window before the work starts, and it is read
by an agent deciding what to do next. That makes its failure mode quiet: a
padded skill is not a slightly worse skill, it is budget spent on text nobody
acts on and a load-bearing sentence read at the same depth as the recap around
it. A skill that restates a command's `--help` is worse still, because the copy
is the one already in context when the question comes up — so it is the one
trusted after the tool changed, and wrong exactly when it mattered.

It lives in the engine repo's own `.sloprail/`, not in the distributed plugin.
It is how this project judges its own skills, not something shipped to projects
that install sloprail; what a project's skills should say is that project's
business.

## The rubric is assembled, not written

Same structure as the sibling `rule-quality`, and for the same reason.
`RUBRIC.md` holds only the **frame** — the judge's job, the conservatism
instruction, the answer shape, and a `<<<META_RULES>>>` marker. The standard
lives in `rules/<name>/RULE.md`, one meta-rule per directory, and
`judge-skill.sh` splices them in at judge time.

So **adding a meta-rule is adding a directory, and never editing a prompt.** The
alternative — one growing rubric file — makes every addition a diff against a
document holding all the others, where a meta-rule cannot be pointed at, cannot
carry its own enforcement status, and cannot be removed without touching text
belonging to something else.

It also separates the failure modes: editing the frame changes how every skill
is judged, editing one `rules/` entry changes exactly one criterion, and a diff
says which happened.

## The meta-rules, and why these four

`high-signal` is the same standard `rule-quality` applies to rules, restated for
the artifact a skill is — the reader is an agent mid-task rather than an author
mid-decision, and the cost of padding is context budget rather than attention.

`help-is-not-skill` is the generalisation of something this repo already tests.
`TestT003_14_SkillDoesNotRestateTheDerivedVocabulary` fails if
`authoring-guardrails/SKILL.md` names more than one event kind in its prose,
because a list of kinds in a skill is the copy an author trusts when a module is
added. That test pins one skill against one vocabulary. The meta-rule states the
principle behind it: generated interface detail belongs to the generator, and
the skill owns the part `--help` cannot carry — which command, when, why this
one, in what order.

The rule deliberately **names no specific command**, and that is not squeamishness
about examples. The discovery command in this repo has already moved once: the
`sr-guardrail` binary was deleted outright, on the argument that a help command
describing a structure rather than a command's behaviour belongs in a skill. Since
that landed, the same vocabulary is reported by `internal/guardrail/validate.go`
at the moment an author is actually wrong, and that is now the only path to it. A
rule citing whichever of those is current would be a rule that goes stale for
exactly the reason it exists, and it would be sent to a model as standard on
every judged skill. So the worked example lives here, in prose no model reads,
and the rule states the shape instead.

## Why the judge may not run commands

The judge is invoked with `--allowedTools "Write"`. It can write its verdict and
nothing else: it cannot run a command, read a file, or see any `--help` output.

That constrains what `help-is-not-skill` is allowed to ask. The natural phrasing
of the rule — "is this a copy of what the command actually prints?" — is a
question the judge structurally cannot answer, and asking it anyway does not
produce abstention. It was tried during authoring, across three rewrites, and
each one returned a confident verdict reasoning from appearance ("would be
generated by `sr-guardrail help`", "would become stale if the binary changes")
because appearance was the only evidence available. A rule whose stated test the
judge cannot perform does not fail loudly; it fails as fluent guesswork.

Granting `Bash` or `Read` would make the test answerable, and was rejected. The
judge's input is a SKILL.md the agent has just written — untrusted text by
construction, since the whole point is to catch what an agent produces — and a
skill legitimately contains command invocations. Handing it execution means
attacker-shaped text nominates the commands that get run. The `--settings`
overlay and the `/tmp` working directory defend against hook recursion and
project-context leakage; neither is a sandbox, and neither would stop a skill
whose "example invocation" is a pipe to a shell. The escalation is real, the
protection is not, and the shape test catches the cases that actually occur.

So the rule judges SHAPE — flag tables, option lists with defaults, subcommand
rosters, verbatim usage blocks — all recognisable in the text itself, and says
so in its own body rather than leaving the limitation implicit. It is weaker
than the semantic test and knowingly so: reference-shaped prose that is not one
of those shapes passes, including a table a project moved out of its binary on
purpose. That asymmetry is the right one, because the false positive it avoids
sends an author to a help output that does not contain what they were told to
find.

`progressive-disclosure` is the one place this guardrail declines to enforce a
number the owner named. 500 lines was called out as a ceiling with "ideally
less" as the real standard, and a judge given 500 would answer the wrong
question: a 480-line skill would pass while padded, and the cheapest way to
satisfy a line cap is to split a bloated skill into two bloated files, which
loads identical bytes and scores better. So the rule states the ceiling, says
plainly that it is not what is enforced, and puts the enforceable question in
its place — does a section only some readers need sit inline instead of behind a
link. Length enters as evidence for that, never as the finding. Cutting text
nobody acts on is `high-signal`'s job, and the two rules are kept from
overlapping on purpose.

`guardrail-is-not-prose` is the rule that closes the loop with the rest of the
system. A prohibition written into a skill is a second copy of a guardrail, and
it goes stale the first time the guardrail is tightened — while the guardrail
itself already refuses at the moment it matters, names itself, and has the
offending text in hand. Examples of correct usage carry the shape without the
copy.

## Why Pre and Post both

The Pre kinds refuse before the bytes land, which is where a guardrail is worth
most. But `PreFileUpdate` cannot always state its result — an edit whose outcome
is not derivable arrives with `resultKnown: false` — and a judge that read the
absent result as `""` would permit every such edit. So the script defers in that
case, and the Post binding judges what actually landed. Neither kind alone
covers the ground.

## Failing open

The judge permits when its OWN machinery fails: no `claude` on PATH, a timeout,
a verdict that cannot be parsed. This overrides the engine's fail-closed default
deliberately. A model call is not a decidable check — it flakes for reasons that
are not evidence about the file — and under fail-closed one flake wedges a
session the agent cannot un-wedge by fixing anything.

The VERDICT still fails closed: a skill the judge flags is refused.

The exception is an empty `rules/`, which refuses. That is not the machinery
breaking around a standard; it is the standard being absent, and a judge with no
criteria cannot find a violation — so permitting would be indistinguishable from
a permanent clean bill of health. A missing `guardrailDir` refuses for the same
family of reasons: it means the payload did not come from the engine, which is a
malformed-payload bug rather than a model failure, and silently permitting there
is the "looks like a pass" trap this project has hit repeatedly.
