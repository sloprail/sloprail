## The failure

An agent reaches for a full rewrite when an append would do. It regenerates the
file from what it currently holds in context — and everything it never read is
silently gone. The diff looks like an edit; nothing errors. The load-bearing word
is *unasked*: the removal was never tied to anything the user actually said, so
content nobody asked to remove disappears along with the change that was
requested.

<UseCase id="destructive-overwrite" label="Watch it happen — then get refused" />

## How it works

Removal is allowed only when it is grounded in the user's own words. A pure
addition passes freely; a removal has to carry a quote of what the user asked,
and that quote has to resolve to something the user really said.

<Steps>

1. A `when` script settles the cheap, deterministic case: pure additions need no
   citation; a removal with no valid grounded quote is refused outright; a
   removal with a grounded quote passes to the judge.

2. A judge rules the two properties only a model can — that the change is clean
   and targeted to what the quote asked, and stated absolutely rather than as a
   narrative of what changed.

</Steps>

This is a **gate with a file-guard of the same name**. The gate runs before the
update lands, while the content that would be lost is still on disk, so the loss
is prevented rather than mourned; it is cheap, with no model in it. The file-guard is
the after-check and carries the judge: it rules on the settled file at Stop, which
catches a rewrite the gate could not see ahead, such as a script.

### gate

Triggers before a memory file is written or deleted (`PreFileWrite` and
`PreFileDelete`). A citation of the user's words is required `when` the change
removes content: additions pass, ungrounded removals are refused
deterministically, and a grounded removal passes to the file-guard's judge at Stop.
A write whose result the engine cannot work out ahead
(`sed -i`, `>`) is refused by `require-known-result.sh`: the gate fails closed
rather than admit bytes nobody saw.
