## The failure

An agent changes code that sits near a business rule and reports that the rule
still holds. Nothing forced it to look. There is no automatic way to confirm the
logic is still correct, so the claim rests on the agent's word, and confirming it
means a person going to read the code by hand. The invariant that mattered most
is the one nothing re-checks, and it stays that way until it breaks in
production.

## How it works

The invariant is pinned to the code with a marker — a note in the source that
names the exact spec lines the code upholds, at a commit. The guardrail keys off
that marker, not off a path, so it fires wherever the marked code lives.

<Steps>

1. A cheap script confirms the pin is real (a commit sha, a line range inside
   the spec) and still lines up with the spec at HEAD, so a stale or moved pin
   is caught before anything expensive runs.

2. A `prepare` step reads the pinned spec lines and hands them to the judge,
   which rules on whether the marked code still upholds that exact wording.

</Steps>

Pinning the code to the spec opens a second way out: rewrite the spec line to
agree with the code, or re-pin the code to looser wording. A second rule,
`pinned-spec-holds`, closes it — as a gate, so the change is refused before it
lands, with a file-guard of the same name as the after-check at Stop. A spec that code pins holds the user's business
rules, so any change to it — a pinned line, a new rule, an exception on a line of
its own — and any write that moves or removes a pin, must cite the user's own
words, and — at Stop — a judge checks that those words ask for that change; for a pinned
line, that they ask for the rule itself to change rather than for a feature that
conflicts with it.

`pinned-invariant` is a plain **file-guard**: it judges the committed files at Stop,
and the markers decide which files carry an invariant and which spec lines are
pinned. `pinned-spec-holds` is a **gate** plus a file-guard: the gate prevents
the change to the rules (a citation requirement, no model), and the file-guard
holds the judge and catches what the engine could not see ahead.

holds the path to the spec convention. `pinned-text.sh`

### pinned-spec-holds: a pinned rule changes only when the user asks

The **gate** triggers before a write (`PreFileCreate`, `PreFileUpdate` and
`PreFileDelete`) and only on the files a pin can involve: specs (`SPEC.md`, or a
`.md` file under `specs/`, the convention `pin.sh` holds every pin to) and files
carrying an `invariant` marker before or after the write. It decides from the
bytes, so it refuses a shell edit it cannot work out ahead (`sed -i`, `>`) on
every file it triggers on — which is why it triggers only on those files:
matching every path would refuse every `sed -i` in the project.
`refuse-unknown-result.sh` is that refusal, and it lets a write through only when
the predicate has decided nothing pinned is at stake.
`changes-pinned-lines.sh` is the `when` of a user citation: it applies the
requirement when the change touches a spec some marker pins (at the committed head
or at the range's base) — any line of it — or moves a marker off the wording it pinned —
marked code moved to another file keeps its pin — and waives it only when it has
decided the write does neither. The judge (with `only-when-pinned.sh`, which asks it
about exactly those writes) lives in the file-guard and rules at Stop.

The **file-guard** of the same name is the after-check. It acts at Stop on the
committed changeset, each file at the range's base against head, and catches what
the gate cannot: a script rewriting a spec, or one command deleting every holder of
a pin. The shared logic of `changes-pinned-lines.sh` is one library; the file-guard's
entry reads the Changeset (`.changeset.files[]`), with the user's words taken from the
commits' `Sloprail-Cites-User:` trailers, and the gate's reads the `Pre*` events.
