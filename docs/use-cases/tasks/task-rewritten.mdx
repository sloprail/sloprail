## The failure

An agent implements part of an ask, then quietly edits the task to describe only
the part it did. The spec now matches the work instead of the other way around,
so every later check passes — the tests cover what's written, the "done" is
honest against a goal that was diluted to fit. The original ask is gone, and
nothing records that it shrank. The goal drifts toward whatever was easy to
finish.

<UseCase id="task-rewritten" label="Watch it happen — then get refused" />

## How it works

The task's ask has to stay tied to its human-authored source. The guardrail
grounds the written ask against the actual message that prompted it, so the ask
can't be rewritten into something the user never said.

<Steps>

1. A script confirms the ask carries a reference to the message it came from —
   no reference, no valid ask.

2. That referenced message is resolved, and a judge rules that the ask is true to
   it and describes only that message — not a narrowed rewrite.

</Steps>

This is a **preventive file-guard**: it runs before the write to the task's ask
lands, so a diluting edit is refused rather than caught after the fact.

### file-guard

Matches the task ask file and runs preventively. The script gates the judge: the
reference must exist, then the resolved message is handed to the model, which
rules that the ask is faithful to it and scoped to only it.
