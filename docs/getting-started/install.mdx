sloprail runs inside your agent as a **plugin**, and its hooks call a separate
set of binaries (`sr`, `sr-session`, `sr-file`, `sr-mark`, `sr-agent`, `sr-eval`). The
plugin installs those itself, so installing the plugin is the whole install.

## Install the plugin

<Tabs>
  <TabItem label="Claude Code">
    ```bash
    /plugin marketplace add sloprail/sloprail
    /plugin install sloprail@sloprail-marketplace
    ```

    Pick the project scope. The hooks are registered; a project with a
    `.sloprail/` directory is now guarded, and a project with none is an
    ordinary project until its first rule.
  </TabItem>
</Tabs>

More harnesses will get their own tab as they go live. The engine's contract —
hook points in, events out — isn't specific to one, so the rules a project writes
don't change between them.

## The binaries

The first session after the install fetches them, once: the GitHub release
matching the plugin's version (never "latest"), verified against the
release's checksums, into `~/.local/bin` (set `SLOPRAIL_INSTALL_DIR` to
choose another directory). The session says it is doing this, and says so
loudly if it fails.

To install them yourself instead, set `SLOPRAIL_NO_AUTO_INSTALL=1` and run

```bash
curl -fsSL https://raw.githubusercontent.com/sloprail/sloprail/main/install.sh | sh
```

or, with Go, `go install ./services/...` from a checkout of
[sloprail/sloprail](https://github.com/sloprail/sloprail). Either way, if the
binaries are missing the next file write is refused with the install command,
never silently let through.

## Verify it worked

```bash
sr-session start < /dev/null
```

should print the load check with no errors. If you skipped step 1 or
`~/.local/bin` isn't on `$PATH`, the very next tool call in your agent will say
so loudly — sloprail never fails silently on a missing install; the guarded
action is blocked with the install command repeated until it can find
`sr-session`.
